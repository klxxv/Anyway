## 1. MVP 可行性重新评估

### 1.1 诚实判断：当前 MVP 产品不可用

在通读了完整代码库之后，产品经理的结论是：**当前 MVP 从"产品可用"的角度来看存在根本性问题——没有数据摄入管道。**

```
用户打开 Research Canvas
  → 看到空白画布
  → "我应该做什么？"
  → 手动创建节点和边
  → 一个假设需要 15 分钟来录入
  → 放弃
```

这不是 UI/UX 问题——这是**产品冷启动问题**。类比：如果 GitHub 要求你在创建仓库时手写 git objects，它不会成功。GitHub 成功是因为 `git push` 让代码摄入变得简单。

### 1.2 目标用户的诚实修正

最初设想的目标用户是"所有实证学科的研究者"。但基于 MVP 的现实：

**真正的早期采用者是 ML/AI 研究者**，原因：

1. **最快的迭代节奏**：ML 领域一个实验周期是几天到几周，传统学科是几个月到几年。迭代越快，组织假设的需求越强。
2. **最熟悉 Git 文化**：ML 研究者几乎都用 Git，理解版本控制和内容哈希。`rc:` 的概念对他们是"Git for science"的自然延伸。
3. **arXiv 预印本文化**：ML 领域 90% 以上的论文先在 arXiv 发布，意味着"未发表的实验结果"已经是合法引用对象。这与注册表的"先注册后出版"模型天然契合。
4. **消融实验是标准实践**：ML 论文几乎都必须包含 ablation study，这使得"消融场景"功能对 ML 研究者有即时价值。

### 1.3 重新定义 MVP

MVP 不应该只是"当前功能的 bug fix + UI polish"，而应该是：
> **让一个 ML 研究者能拖入一篇 PDF，自动生成图谱，然后在此基础上做消融分析和逻辑链追踪。**

这是一个更高的标准，但它明确了一点：没有 PDF→Canvas 的数据摄入管道，一切功能都是空中楼阁。

## 2. 冷启动解决方案：PDF→Canvas Agent

### 2.1 为什么这是唯一的杠杆解

考虑所有可能的冷启动解决方案：

| 方案 | 用户操作 | 可行性 | 杠杆效应 |
|------|---------|--------|---------|
| **手动创建节点** | 阅读论文→逐条输入 | ✅ 已实现 | ❌ 15 分钟/假设，不可规模化 |
| **导入 BibTeX** | 从 Zotero 导入元数据 | 🟡 可行 | ❌ 只能导入论文元数据，不是主张 |
| **PDF→Canvas Agent** | 拖入 PDF→自动提取 | 🟡 需要构建 | ✅ 分钟级摄入整篇论文的全部主张 |
| **Zotero 同步** | 从 Zotero 库一键导入 | 🟡 可行 | 🟡 解决文献管理，不解决主张提取 |
| **社区图谱共享** | 浏览并复用他人的图谱 | 远期 | ✅ 网络效应，但需要冷启动 |

**结论**：PDF→Canvas Agent 是唯一能把冷启动从"不可能"变成"可能"的方案。其他方案要么不是杠杆（手动输入），要么解决的是不同的问题（Zotero 同步解决文献管理，不解决主张提取）。

### 2.2 PDF→Canvas Agent 的三阶段产品化路径

**Phase A：内置 Agent（当前 MVP 缺失的关键一环）**

```
用户拖入 PDF（或 arXiv URL）
  → Agent 提取结构化信息
    ├─ 识别假设（hypothesis）
    ├─ 识别变量（variable，含取值范围）
    ├─ 识别方法（method）
    ├─ 识别实验设置（experiment）
    ├─ 识别结果指标（result + metric）
    └─ 识别证据来源（evidence，带 section/para/sentence anchor）
  → Agent 提议关系（supports/contradicts/depends_on）
  → 生成 GraphPatch 建议
  → 用户审阅 → 接受/拒绝/修改
  → 形成图谱
```

关键设计原则：
- Agent 的输出是 **GraphPatch 建议**，不是直接修改。人审阅是必须的门控。
- Agent 标记 `provenance.origin = "ai"` 和 `modelId`，保持完整的来源追溯。
- 用户可以在 Agent 提取的基础上修改——Agent 是"第一稿"，人是"终稿"。

**Phase B：可配置 Agent（生态系统起点）**

- 不同的提取策略（不同学科、不同论文格式）
- 用户可配置提取模板（"我关心方法 × 结果，不关心相关工作"）
- Agent 的质量反馈循环（"你这次漏了这个假设"）

**Phase C：社区 Agent（协议网络效应）**

- 社区贡献的 Agent（特定学科、特定期刊格式）
- Agent 市场/"Agent store"
- Agent 间的图谱合并（Cross-Canvas Diff）

### 2.3 战略转变："建造工具" → "理解工具"

当前 MVP 是"我给你一个空白画布和强大的图算法，你来组织你的研究"。这个模型对已经知道自己需要什么的人是好的——但这些人不存在。

正确的战略转变：

```
旧模型：建造工具（build tools）
  "这是一套强大的图算法，你来构建你的研究图谱"
  → 用户："我的研究在哪里？"

新模型：理解工具（understanding tools）
  "拖入你的论文，我来帮你理解它的结构"
  → Agent 提取结构 → 用户参与 → 图谱形成
  → 然后图算法帮你发现你不知道的东西
```

这意味着产品叙事从"组织你的研究"转变为"理解你的研究"。前者假设用户已经有清晰的研究结构需要组织；后者承认用户需要帮助来理清他们阅读的东西。

## 3. 两层 Diff 的边界

### 3.1 精确区分两个容易混淆的概念

**Canvas Diff（结构 diff）** 和 **Cross-Canvas Diff（语义 diff）** 是两个完全不同的东西，运行在不同的层上：

```
┌─────────────────────────────────────────────────────────┐
│                    内核层（Rust graph_compiler）          │
│                                                         │
│  Canvas Diff（结构 diff）：                               │
│  输入：ProjectState_v1, ProjectState_v2                  │
│  输出：{ addedNodes, removedNodes, modifiedNodes,        │
│           changedBlockHashes, addedEdges, removedEdges } │
│                                                         │
│  确定性算法，二进制安全，bit-identical 双实现验证          │
│  不涉及语义理解——只比较结构                               │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                    Agent 层（LLM + 图计算工具）            │
│                                                         │
│  Cross-Canvas Diff（语义 diff）：                         │
│  输入：来自论文 A 的图谱 + 来自论文 B 的图谱               │
│  步骤：                                                  │
│    1. LLM 识别语义等价：论文 A 的 n-h1 "RoPE 对长上下文    │
│       至关重要" ≈ 论文 B 的 n-h3 "位置编码是长序列的必要    │
│       组件"（措辞不同，含义相同）                          │
│    2. LLM 识别矛盾：论文 A 声称 X（证据链完整），           │
│       论文 B 声称 not-X（也有证据链）                      │
│    3. LLM 提议跨图边：在两个图谱的节点之间插入              │
│       supports / contradicts / derived_from 边           │
│    4. 产出 → PluginGraphPatch（review-gated）             │
│                                                         │
│  用户接受后：                                             │
│    5. 内核验证合并后的图谱不变式                          │
│    6. 内核重新计算可达性、逻辑链、反驳链                   │
│    7. 形成统一的跨图谱分析视图                            │
└─────────────────────────────────────────────────────────┘
```

### 3.2 为什么这个边界至关重要

1. **Canvas Diff（结构）必须进内核**：它是确定性图计算问题。应该在 Rust graph_compiler 中实现，与 blockHash/fileHash、逻辑链、反驳链在同一个二进制安全层。LLM 绝不能执行结构 diff——它不保证确定性。

2. **Cross-Canvas Diff（语义）必须在 Agent 层**：它涉及语义等价判断（"这两句话意思相同吗"），这是 LLM 擅长的。但 LLM 的输出是提议（proposal），不是结论（conclusion）——人审阅门控保证质量。

3. **内核是"计算引擎"，Agent 是"提议引擎"**：内核永远输出确定性结果；Agent 永远输出需要人审阅的建议。这条线不能模糊。

### 3.3 对产品架构的影响

- `src-tauri/src/graph_compiler.rs` 应新增 `diff()` 函数（Canvas Diff）
- Cross-Canvas Diff 应实现为一个 Agent（在 Agent 层，可能作为官方插件）
- 两个 diff 的 API 边界清晰：`graph.diff(state1, state2)` vs `agent.crossCanvasDiff(graphA, graphB)`

## 4. 五个官方插件的战略评估

### 4.1 当前五个官方插件

| 插件 | 当前状态 | 评估 |
|------|---------|------|
| **Git Experiment** | ✅ 已实现 | 核心价值——实验的 provenance 追踪 |
| **Python** | 🔧 保留接口 | 实验笔记本桥接——ML 研究者必备 |
| **Zotero** | 🔧 保留接口 | 文献管理入口——最广泛使用的工具 |
| **MCP** | 🔧 保留接口 | Agent 的标准化协议——未来价值高 |
| **Review-Gated Agent** | 🔧 保留接口 | AI 建议的安全门控——安全基础 |

### 4.2 逐插件分析

**Git Experiment**（P0，已实现）
- 价值明确：实验代码的版本化追踪
- 不需要改变

**Python / Jupyter**（P1，高优先级）
- 这是 ML 研究者的核心工作流
- 桥接方向：Jupyter cell → 输出指标 → 自动创建 experiment 节点 + result 边
- 不是"替代 Jupyter"，而是"Jupyter 的实验结果自动流入图谱"

**Zotero**（P1，高优先级）
- 文献管理是入口，不是终点
- 桥接方向：Zotero 条目 → PDF → PDF→Canvas Agent → 图谱
- Zotero 管理论文，Research Canvas 管理论文中的主张
- 与 Zotero 的关系应是"互补"，不是"替代"

**MCP**（P2，远期价值）
- Model Context Protocol 是 Agent 间通信的标准化方向
- 但目前 Agent 还没有做出来，MCP 插件是"先有接口，后有价值"
- 建议：保留接口，不急于实现

**Review-Gated Agent**（P0，安全基础）
- 这不是一个"插件"——它是所有 Agent 的安全基础
- `graph.patch.propose` → review → accept/reject 的模式不应改变
- 建议：不改变当前架构

### 4.3 建议调整

- **Canvas Diff 进内核**：它不是"插件"，它是内核功能。从插件列表中移除，进入 graph_compiler
- **新增 Cross-Canvas Diff Agent**：替代当前五个插件列表中的 "Canvas Diff"（如果列表中包含的话），明确它是 Agent 层功能
- **Zotero Agent 分阶段**：Phase 1 只做元数据导入（低风险），Phase 2 做 PDF→Canvas（高价值但需要 Agent）

## 5. 注册表是什么

### 5.1 不是区块链

首先澄清一个重要误解：注册表**不是区块链**。

| 属性 | 区块链 | Research Canvas 注册表 |
|------|--------|----------------------|
| **共识机制** | 需要（PoW/PoS/...） | 不需要——透明日志 + 独立验证 |
| **去中心化** | 通常需要 | 不需要——可以中心化运行，因为任何人都可以独立验证 |
| **代币** | 通常有 | 没有也不会有 |
| **数据模型** | 交易列表 | 签名断言（signed assertions） |
| **验证方式** | 需要信任共识 | 不需要信任——验证哈希和签名 |

注册表的核心模型是**透明日志**（transparent log）——类似 Certificate Transparency：

```
注册表 = 一个只能追加的日志
  ├─ 每条记录 = { assertion, Ed25519 签名, RFC3161 时间戳 }
  ├─ 任何人都可以验证：
  │   ├─ 签名是否有效（Ed25519 公钥验证）
  │   ├─ 时间戳是否在签名之后（RFC3161 验证）
  │   └─ 内容哈希是否与声明的 blockHash 一致（SHA-256 验证）
  └─ 不需要信任注册表运营商——信任在密码学里
```

### 5.2 完整工作流程

```
研究者创建假设节点 "RoPE 对长上下文至关重要"
  → 本地 Ed25519 签名（私钥从不出设备）
  → 提交到注册表
  → 注册表返回：{ receiptId, RFC3161 timestamp }

六个月后，另一个团队发表类似发现
  → 研究者在注册表中查到自己的签名 + 时间戳
  → 优先权已被密码学证明

第三方验证：
  → 下载注册表日志
  → 验证签名、时间戳、内容哈希
  → 结论："研究者 A 在 2026-03-15 首次注册了该假设"
```

### 5.3 与论文出版的对比

| 维度 | 传统论文出版 | 注册表 |
|------|------------|--------|
| **时间** | 投稿→审稿→出版：6-18 个月 | 注册：即时 |
| **粒度** | 整篇论文 | 单个假设/变量/实验 |
| **验证** | 依赖出版商 | 独立密码学验证 |
| **优先权** | 出版日期 | 注册时间戳 |
| **可争议** | 撤稿（罕见且困难） | 自然支持反驳链和消融验证 |

### 5.4 注册表不是替代论文出版

这是一个重要的澄清：注册表**不是**要替代论文出版。出版有它的价值——叙事、背景、文献综述、完整的论证弧线。

注册表补充的是出版做不到的事：**精确的、可验证的、即时的优先权声明**。

类比：Git commit 不是要替代技术博客。博客有它的价值。但 commit 给了你一个博客做不到的东西：不可篡改的、时间戳保护的代码版本记录。

## 6. 从产品到协议：Research Canvas 的协议化路径

### 6.1 核心洞察

产品经理的洞察：Research Canvas 瞄准的不是"做一个更好的研究工具"——它瞄准的是"成为科学主张引用的一层新基础设施协议"。

这是一个质的差异。类比：

| 协议 | 解决的问题 | 核心创新 | 成为基础设施的时刻 |
|------|----------|---------|------------------|
| **HTTP** | 文档之间如何互相引用 | URL——每个资源有唯一地址 | 浏览器和服务器独立实现同一套 GET/POST 语义 |
| **Git** | 代码如何版本化且不可篡改 | 内容寻址——commit hash 是内容的指纹 | GitHub/Lab/Gitea 三家竞品共用一个底层协议 |
| **SMTP** | 邮件如何跨组织路由 | 信封格式——from/to 字段独立于邮件内容 | 任何一个邮件服务器都能和任何另一个互通 |
| **DOI** | 论文如何被永久引用 | 间接层——DOI 解析到当前 URL | 所有期刊都注册 DOI，所有引用格式都支持 |
| **`rc:`** | 科学主张如何被精确引用 | 内容寻址——blockHash 是主张的指纹；fileHash 是版本的指纹 | **尚未发生——这是 Research Canvas 的机会** |

DOI 引用的是**论文**（一个容器）。`rc:` 引用的是**论文里的一个主张**（容器里的具体内容）。这是往下沉了一层的协议。

### 6.2 为什么这个协议层现在是空白的

不是因为没人想过，而是因为三个前提条件最近才同时满足：

**1. 内容哈希成为社会共识**

十年前你跟研究者说"用 SHA-256 给假设做指纹"，得到的反应是"什么？"。今天：
- Git 普及了"commit hash = 不可篡改的版本指纹"的直觉
- 区块链/Wikipedia/IPFS 普及了"内容寻址"的直觉
- 每个 ML 研究者都用 Git，知道 hash 是什么

**2. 结构化科学数据开始脱离 PDF**

十年前论文的"原子单位"是 PDF 页面。今天：
- arXiv 支持 HTML 全文
- PubMed Central 有结构化 XML
- 预印本文化让"未发表的实验结果"成为合法引用对象
- 消融实验表格已经是 ML 论文的标准组件

**3. LLM 让"提取主张"的边际成本趋近于零**

这是最关键的一点。五年前，"从 1000 篇论文中提取所有假设并对比"需要 1000 个人-小时。今天，一个 PDF→Canvas Agent 可以在几分钟内完成。这意味着**协议的数据供给端**突然变得可行——不像五年前，协议的采纳只是不可能的空想。

### 6.3 五阶段协议化路径

类比 Git。Git 不是从"版本控制协议"起步的——它从"Linus 需要一个更好的 patch 管理工具"起步。然后 GitHub 把协作体验做好了，然后 Git 的对象模型（blob/tree/commit/tag）变成了事实标准，然后 CI/CD 工具、代码托管平台、IDE 都围绕这个标准构建。

```
Phase 1（当前）：Research Canvas 是唯一的 rc: 生产者和消费者
  → 协议 = 产品的内部格式
  → 没有其他人产生或消费 rc: 引用

Phase 2：注册表上线
  → 研究者开始在注册表上注册主张
  → "rc: 引用"出现在 Research Canvas 导出的论文中
  → 审稿人可以验证引用的完整性

Phase 3：第三方开始消费
  → 学术搜索引擎索引 rc: 引用
  → 期刊论文中出现 rc: 引用（手动插入）
  → arXiv / OpenReview 开始支持 rc: 引用显示

Phase 4：第三方开始生产
  → 其他工具生成 rc: 兼容的图谱
  → 注册表成为中立基础设施
  → 协议规范独立于 Research Canvas 产品

Phase 5：协议成为基础设施
  → 学术引用标准包含 rc: 作为一等引用格式
  → 基金评审要求 rc: 注册
  → 科研诚信调查使用 rc: 图结构
```

### 6.4 两个诚实挑战

**挑战 1：先有鸡还是先有蛋**

协议需要用户才有价值，用户需要协议才能被吸引。这是所有协议项目的核心挑战。

缓解策略：产品先于协议。Research Canvas 先作为**产品**获得用户（Phase 1-2），在用户使用过程中自然产生 `rc:` 引用。当引用数量足够多、足够有用时，协议叙事才变得可信。

**挑战 2：学术出版界的保守性**

学术出版界的决策周期以十年为单位。DOI 从提出到广泛采用用了十年。`rc:` 可能面临同样的时间线。

缓解策略：不从出版界切入，从研究者切入。ML 社区的研究者已经在用 arXiv、GitHub、Twitter 构建自己的学术身份，不完全依赖传统出版。如果研究者先采用，出版界会跟随。

## 7. 投资人视角的估值分析

以下是如果以 AI 投资人的视角评估 Research Canvas 的种子轮估值。这不是真实的融资计划——这是战略思维练习，帮助团队理解项目的价值锚点和叙事杠杆。

### 7.1 投资判断：会投吗？

**会，以种子轮的条件。** 但估值取决于对"协议故事"的信服程度，而非当前产品的 traction（因为当前 traction 为零）。

### 7.2 估值框架

早期投资估值不是 DCF 模型，是**团队 × 赛道 × 时机 × 叙事**。

#### 7.2.1 团队（从代码推断）

| 信号 | 判断 |
|------|------|
| 架构决策 | **强正信号。** Rust 内核 + TypeScript 类型 + React 渲染三层分离，边界清晰。WASM 沙箱 + capability 模型。这不是"先跑起来再说"的代码——这是在为 5 年后的协议化做准备。 |
| 安全意识 | **强正信号。** `.myc` 安装校验（API 版本、遍历路径、展开大小、WASM 魔术数、manifest 身份）。`graph.patch.propose` review-gated。这些是基础设施级的 paranoid，不是 MVP 思维。 |
| 工程完成度 | **强正信号。** i18n 从第一天就有中英文。响应式验证了四个 viewport。15 个 workspace 测试 + Rust 原生测试。design-qa.md 记录了 10 轮迭代。这不是 demo——这是认真做的产品基础。 |
| 产品直觉 | **待验证。** PDF→Canvas Agent 的冷启动洞察是正确的。但还没有证据表明团队能把 Agent 做出来——当前 GraphPatch 的三条建议是 hand-crafted fixture。 |

**团队评分：8/10（技术执行），待验证（产品交付）**

#### 7.2.2 赛道

**不是"AI 工具"赛道，是"科学基础设施"赛道。**

这个赛道的特征：
- TAM 不大（全球活跃研究者 ~8M），但 ARPU 可以很高（机构采购、基金授权）
- 决策周期长（学术采纳以年为单位），但一旦采纳，切换成本极高（网络效应）
- 不是一个 winner-take-all 市场（不同学科可能需要不同工具），但协议层是 winner-take-most

可比交易：
- **Semantic Scholar**（Allen Institute 内部孵化，非独立融资）：证明"结构化科学知识图谱"有价值
- **Consensus**（AI 研究搜索）：$110M Series A (2024)，证明"AI × 学术搜索"能融资
- **Elicit**（AI 研究助手）：$9M seed (2022)，证明"LLM 辅助文献分析"是投资人认可的方向
- **Overleaf**（协作 LaTeX）：被 Digital Science 收购，估值 $25-50M estimated
- **ResearchGate**：$200M+ valuation at peak，证明"研究者社交网络"的价值上限

**这些可比项目没有一个是"协议层"的。它们都是应用层。Research Canvas 的协议故事在可比项目中找不到对标——这对估值来说既是风险（没有参照物），也是机会（上限更高）。**

#### 7.2.3 估值情景

**Scenario A：协议叙事成立（$12-18M seed）**

前提条件：
- PDF→Canvas Agent 功能演示成功（不只是 demo，能处理任意 PDF）
- 注册表 MVP 上线
- 有 3-5 个活跃的研究团队使用（不是 1000 个注册用户，是真正在用的人）
- `rc:` 协议规范草案发布

叙事："这是科学引用的新协议层。就像 DOI 取代了 URL 作为论文的永久标识符，`rc:` 将取代 'Smith 2024' 作为主张的永久标识符。TAM = 整个科学出版市场。"

**Scenario B：产品叙事（$6-10M seed）**

前提条件：
- 当前 MVP + 性能优化 + 教程
- 有一些用户但网络效应未形成
- 没有注册表

叙事："这是一个面向 ML 研究者的专业研究组织工具。比 Obsidian 更适合研究推理，比 Notion 更适合学术工作流。TAM = 全球 ML 研究者 ~500K。"

**两者之间的差距（2-3x）来自叙事层级的不同。**

### 7.3 三层护城河

| 护城河层级 | 内容 | 可复制性 |
|-----------|------|---------|
| **L1：产品执行** | UI、插件、集成 | 🟡 可被复制——好产品总会被追赶 |
| **L2：图计算内核** | Rust graph_compiler、内容哈希、消融场景 | 🟢 可复制但成本高——需要 rust + crypto + graph theory |
| **L3：协议网络效应** | `rc:` 引用网络、注册表、生态 | 🔒 不可复制——网络效应一旦形成，切换成本无限大 |

L3 是唯一真正持久的护城河。这也是为什么协议叙事对估值的影响如此之大——它决定了护城河的上限。

## 8. 护城河：形式逻辑 vs 概率推理

### 8.1 核心洞察

产品经理的洞察：**Research Canvas 面对大模型的壁垒在于逻辑链是一个不能用概率描述的链条，而必须要和形式逻辑一样准确。这能成为一道护城河——让 Canvas 数据更加宝贵和对人类富有价值。**

这个洞察非常精准。LLM 和形式逻辑链之间有不可逾越的质的差异——不是"准确率 80% vs 95%"的量的差异，而是**计算模型**的根本不同。

### 8.2 计算模型的根本差异

```
LLM 的"推理"：                     Research Canvas 的逻辑链：

P(token | context)                  A ──supports──► B ──supports──► C
     ↓                                          ↓
"ReLU 可能对深度网络至关重要，         BFS( A, {edgeTypes: ["supports"]} )
 因为它在之前的研究中表现良好…"              ↓
                                    BFS 退出的条件是：B 存在一条 supports 边
                                    从 A 出发，C 存在一条 supports 边从 B 出发。

                                    不管运行多少次，不管在什么机器上，
                                    结果永远是 {A, B, C}。

                                    没有"可能"。
```

### 8.3 为什么概率不能替代形式准确

考虑一个真实的科学反驳场景：

**论文 A 声称**："RoPE 对超过 8k 上下文长度的 Transformer 至关重要。证据：去掉 RoPE 后 16k 上下文准确率从 73.2% 降到 66.8%。"

**论文 B 声称**："RoPE 可以被 ALiBi 替代，且在 16k 上下文下结果持平。证据：ALiBi 在 16k 上下文达到 72.9% 准确率。"

**LLM 读两篇论文后的"推理"：**
> "论文 B 的发现似乎与论文 A 部分矛盾。不过论文 A 的实验设置与论文 B 不完全相同，因此直接比较可能存在误导。总体而言，RoPE 的有效性可能取决于具体的实现细节…"

这是**概率性摘要**——它把两篇论文的内容压缩成一段听起来合理的文字，但它无法做以下任何一件事：

**Research Canvas 的形式逻辑链能做到的：**

1. **检测精确矛盾**：内核发现"论文 A 的 claim 与论文 B 的 claim 之间存在 contradicts 路径"，且两条路径都连接到了同一块 evidence（"16k 上下文准确率"）。这不是概率判断——这是图结构上的可达性计算。

2. **消融验证**：生成场景"去掉论文 A 的 RoPE 变量"→ 内核计算可达性变化 → 发现论文 B 的 claim 失去了一个支撑来源，但并未被反驳——"ALiBi 替代 RoPE"的 claim 独立成立，与"RoPE 至关重要"的 claim 在证据层上存在差异（A 的基线 73.2% ≠ B 的基线 72.9%）。

3. **最小矛盾集**：矛盾不在于"RoPE vs ALiBi"，而在于两个实验使用了不同的基线准确率。Canvas 能精确指出矛盾的最小集合——这是 LLM 做不到的。

### 8.4 护城河随 LLM 进步而加深，而非变浅

这是一个反直觉但至关重要的洞察：

许多 SaaS 产品担心 LLM 变得更好会侵蚀它们的价值。但 Research Canvas 的情况正好相反：

```
LLM 变强 → 更多论文 → 更多相互矛盾的 claim → 更需要形式逻辑链来分辨

LLM 能生成看似合理的"科学推理" → 区别真假推理的需求更大
  → 信任从 LLM 输出转移到可验证的图结构

LLM 的幻觉问题无法根本解决（概率引擎的本质）
  → 形式逻辑链成为区分"人经过验证的研究"和"LLM 生成的噪音"的唯一方式
```

**LLM 越强，科学文献中的信号-噪音比越低。信号-噪音比越低，形式逻辑链的价值越高。**

### 8.5 护城河完整表述

> Research Canvas 的护城河不是"我们有 AI 功能"——LLM 的 AI 功能是通用的、可复制的。护城河是：**当 LLM 把你的论文变成图谱后，Research Canvas 是唯一能对该图谱执行确定性逻辑链计算的环境**。这不是 AI 问题，这是数学问题（图论）+ 工程问题（内容哈希 + 密码学签名）+ 网络问题（注册表）。三者叠加形成了 LLM 无法跨越——也永远无法跨越——的护城河。

## 9. 关键结论

1. **当前 MVP 有根本性的冷启动问题**：没有数据摄入管道，产品的核心循环无法启动。PDF→Canvas Agent 是唯一的杠杆解。

2. **产品叙事应从"建造工具"转变为"理解工具"**：用户不是带着清晰的研究结构来的——他们需要帮助来理解他们阅读的东西。

3. **Canvas Diff（结构）应进内核，Cross-Canvas Diff（语义）在 Agent 层**：两者的边界不能被模糊。内核做确定性计算，Agent 做概率性提议。

4. **插件列表需要重新评估**：Canvas Diff 不是插件——它是内核功能。应新增 Cross-Canvas Diff Agent。

5. **注册表不是区块链**：它是透明日志 + 密码学验证模型。不需要共识机制，不需要代币，不需要去中心化。

6. **`rc:` 有成为基础设施协议的潜力**：三个前提条件（内容哈希共识、结构化科学数据、LLM 提取成本趋零）最近才同时满足。这是历史性的窗口。

7. **协议叙事的估值是产品叙事的 2-3 倍**：不是因为泡沫，而是因为协议层的 TAM 和护城河上限都远高于应用层。

8. **LLM 越强，Research Canvas 的护城河越深**：这是一个反直觉但正确的结论——因为 LLM 越强，科学文献中的信号-噪音比越低，形式逻辑链的价值越高。

9. **下一步最关键的动作是构建 PDF→Canvas Agent**：没有它，以上所有战略讨论都只是讨论。有了它，产品从"不可用"变为"可用"。
